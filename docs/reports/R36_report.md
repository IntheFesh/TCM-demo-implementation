## 二、流式：难的不是流起来，是流不起来的时候说得出为什么

R32 的教训（演示跑的配置从来没被测过）在流式上会以另一种形状重演：界面转着圈，
而没人能区分「模型在想」「后端不支持流式」「best-of-N 这一路不流式」「真卡住了」。
所以这一轮的设计重心在**可解释**：

```
LLMBackend.SUPPORTS_STREAMING      这个后端能不能真流式（默认 False）
LLMBackend.STREAMING_IS_SIMULATED  流式是不是切出来的（回放后端 True）
LLMBackend.streaming_note()        一句人话：为什么这次没有增量 / 为什么它是假的
```

`generate()` **只在 `SUPPORTS_STREAMING=True` 时才把 `on_delta` 往下传**：
不支持的后端连这个关键字都不该收到——收到要么 TypeError，要么被 `**kwargs`
静默吞掉，而后者更糟（前端永远等不到增量，没人知道为什么）。

三件不许省的实现细节，每条都有测试：

1. **`stream_options={"include_usage": True}` 必须开。** 流式响应的 usage 只在
   最后一个空 `choices` 的 chunk 里；不开的话 `record_usage` 一次都收不到，
   manifest 的 `cache_hit_ratio` 静默变 None——R21 那个坑换到流式这条路上的
   同一个形状。
2. **思考与正文分两路。** 推理模型把思考放在 `delta.reasoning_content`，
   合成一路的话前端会把思考过程当方药渲染出来；而返回给
   `model_validate_json()` 的那份**只含 content**，拼进思考就没有一次能过校验。
3. **增量要合并再发。** 一个 token 一帧 SSE 的话一次 S3 几千帧，前端每帧
   JSON.parse + 重排；人眼分辨不出 30ms 和 120ms。判据是"攒够 80 字
   或距上次 ≥120ms"，收尾无条件冲一次。**有一条测试断言合并后的文本逐字节
   等于模型原始输出**——少一段的表现是前端拼出来的 JSON 解析失败，
   而那时人会去查前端。

事件契约（每位医家自己的子序列，不是全局序列）：

```
physician_start →（react_step…）→ s3_start → s3_delta × n → s3_done → physician_done
```

`s3_done` 带 `events / chars_content / chars_reasoning / first_delta_s /
streaming_note`。前端：`s3_delta` **不进日志**（几十帧会把日志顶得看不见），
只刷一个独立的流式区（`#s3-stream`，`requestAnimationFrame` 合并重排、
只留尾部 1200 字且截断处显示省略号）；`heartbeat` 也不进日志。

## 三、把 120 秒调成 600 秒 —— 一条被明令禁止的改动为什么现在是对的

R9 定读超时 120 秒时，那条测试的注释写着：「这条钉住那个区间，**防止有人
随手调成 600**」。这一轮真的调成了 600。变的不是判断力，是被量的东西：

| R9 那时 | 现在 |
|---|---|
| S3 一次调用实测 6~8 秒 | 提示词带 1.1 万~3 万 token 知识块（R32 起） |
| 输出是 `S3Syndrome` | 输出是 `S3Structured`（五步链 + 五家影响 + 本体引用），长一倍以上（R33 起） |
| —— | S3 **开着思考**，`reasoning_effort` 在 full_context 下是 `max`，推理 token 算在同一次响应里 |

**非流式调用整个响应是一次 socket 读**，读超时盖不住整代生成时间的表现不是
"快速失败"，是**三倍的钱换一个超时错误**（`generate()` 会重试两次，每次都在
同一个地方超时）。

放宽不等于放弃兜底：`deadline`（墙钟）仍然是 read 的 1.5 倍，R8 段 6 那个
"设了 timeout=120 还是卡 46 分钟"的洞照样堵着——它堵的是"对方细水长流地吐字节"，
跟这个数调多大无关。区间断言从 `100~180` 改成 `500~900`，**并且在测试里留下
这段历史**（教训记 `data/SOURCES.md` 第 92 条：一条"不许调大"的注释必须写清
它依赖的测量，否则后来的人只能二选一——照着结论走，或者推翻结论而不知道
自己漏了什么）。

## 四、best-of-N 默认 3 → 1：同一件事不付两次钱

R22 给 S3 加 best-of-N（采 3 次、按 `score_formula` 挑分最高的一张）。
R34 之后那件事有了更强的做法：**符号验证器**拿本体原文判 veto/revise，
判据可核、反例可读、改不好的不下发。两者叠着用等于同一件事付两次钱——
S3 调用数三倍、墙钟跟着三倍，而验证器的闭环最多还要再开 3 次。

| 配置 | 一次问诊的调用数 | S3 产出字数 |
|---|---|---|
| R22~R32（legacy、3 位医家、N=3） | 11 | —— |
| R33~R35（structured、N=3） | 5 | 基准 |
| **R36（structured、N=1）** | **3** | **−67%** |

旋钮留着（`S3_BEST_OF_N=3` 原样可用），R38 的消融要拿它当对照组。
README 里那两个额度默认值（`QUOTA_PER_IP_DAILY_CALLS` 等）**不是手抄的数**，
它们是 `calls_per_consult() * 5`；这一轮顺手把 README 里"= 2 + 3×3 = 11"
那段自 R33 起就过期的算式改成按模式分支的写法（R33 改了默认模式却没同步它，
这是"手抄数字漂第五次"的雏形，趁它还没进报告先掐掉）。

## 五、S1+S2 合一：实现了，**默认关**，理由是次序不是性能

`S1S2_MERGED=1` 把症状标准化与证素推断合成一次调用，省一次 2~4 秒的往返。
两步之间没有第三方数据依赖，看起来是纯性能改动。**但它们之间有一道闸**：

```python
s1 = normalize(complaint)
reject = check_safety([complaint] + s1.symptoms + s1.unmapped)   # ← 闸在这
s2 = infer_elements(s1)
```

CLAUDE.md 的铁律是「**危重症状的拦截必须发生在证素推断之前**」。合一之后，
拦截最早只能早到"那一次调用之前"，也就是只能拿**原始主诉的字面**去查。
而这道闸之所以放在 S1 **之后**，正是因为 S1 归一之后才会露出危重词
（原文「呕吐咖啡色物」→ 归一「呕血」；含糊的病史陈述被归进 `unmapped` 同理）。

处理：那条路完整实现、有 23 条测试、随时可开（R38 的消融要量"合一之后证素
质量变没变"），但**默认关**；打开时命中否决的请求照样**丢掉已推出的证素、
返回 `s2: null`**，对外行为跟分两次那条路逐字段一致（有测试逐项比对）。

为什么不值得：**收益是一次 2~4 秒的调用，代价是把一条结构性保证换成一条流程
约定**，而本轮的调用数验收（≤4 次）不靠它也达到（3 次）。"丢掉算出来的东西"
和"根本没算过"在代码审查里看起来一样，在出事时不一样。教训记 SOURCES.md 第 93 条。

**如果你要的是默认开**：改 `core/llm.py::S1S2_MERGED_DEFAULT = True` 一行即可，
测试与文档都已经覆盖两条路；但请连带决定"原始主诉字面查不出、S1 归一后才露出
的危重词"这一类要不要接受。

## 六、顺带修掉的三个缺陷

**一、`bench_consult` 自 R33 起在默认配置下从未跑通过一次。** 它拿
`len(physicians_enabled())` 当"应该有几条结果"的期望值，而 R33 起产品默认是
structured——五家融合成**一份**结论。实测 `--backend fake` 是
「0/1 次跑成功」、错误写着「只有 1/3 位医家跑出了结果」。
一个性能基准脚本在产品默认配置下跑不通、而没人发现，因为它退出码是 0
（`invalid_reason` 只写进报告、不改退出码）。修法：期望值问
`physicians_for_mode(mode)`，跟 `calls_per_consult` 问的是同一处。

**二、`consult()` 成功路径上 S1/S2 段的调用数写死 2。** 这一轮把它改成
`s1s2_calls`（合一 1 / 分开 2）时漏了一处——正好是最主要的那条返回路径，
因为它的格式是跨行的 `2\n + extra_calls`，跟另外三处的单行写法不同，
批量替换没命中。**是新写的那条断言（"合一之后总数 = 1 + 残差 + S3"）当场抓到的**，
不是读代码发现的。

**三、R34 欠的那项：`ontology_coverage_of_corpus` 每次 manifest 都重读 1MB 的
`cases.json`。** 实测 33ms/次（R34 报告里估的是 52ms，按实测改）。按
`(路径, mtime_ns, size)` 缓存药名计数之后 **0.7ms**（≈48×）。缓存三条纪律跟
`build_entry_index` 那处一致：调用方自带路径的那一路不碰缓存、空结果不缓存、
键带文件签名（重抽语料自然失效）。

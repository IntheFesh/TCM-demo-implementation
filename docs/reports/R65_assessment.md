## 一、本体外的 872 个药名是什么（`scripts/diagnose_expansion_candidates.py`）

四源共 1735 个药名，**872 个在我们 1232 味之外**：

| 分类 | 味数 | 占比 |
|---|---|---|
| 本体里完全没有的药 | **452** | 51.8% |
| 与某个正名差一个字（不可自动归并） | **391** | 44.8% |
| 同株不同药用部位（是另一味药） | 22 | 2.5% |
| 多药串解析碎片 | 7 | 0.8% |

**结论是一个"不能这么做"：按字符串相似度自动分 (a)/(b) 不可靠。** 两次尝试都
产出危险的假阳性：

- 编辑距离 1：`三七叶 ~ 三七`、`丝瓜子 ~ 丝瓜`——同株不同部位，性味功效不同，
  归一等于开错药（跟南北五味子同一类错误）；
- 加部位守卫后仍有：`人尿 ~ 人参`、`冰糖 ~ 冰片`、`升药 ~ 升麻`、`䲡鱼 ~ 衣鱼`。

中药名差一个字通常是**另一味药**，判据不在字符串里。所以：
**扩别名不是扩药材数的替代品**，那 391 个必须人工过（R59 就是这么做的）。
脚本的价值是把要人工看的从 872 缩到 391。

### 扩到 ~1700 味的影响面

**"会动图谱节点数"这个顾虑不成立——药材根本不是图谱节点。**
`data/graph.json` 2356 个节点：证型 174 + 证素 20 + 症状 1087 + 医案 1075，
**药材 0 个**。

| 会动的 | 具体 |
|---|---|
| 7 份测试断言 1232 | `test_ontology_coverage` / `test_node_explain_sections` / `test_warmup` / `test_formula_verifier` / `test_verifier_speed` / `test_chain_parallel` / `test_ontology_gap_attribution` |
| RESULTS.md 两格凭据 | 「药理层归并后」与「本草空槽」 |
| 空槽分母 | 1232×6=7392 → ~1700×6=10200，**缺口百分比会变差而绝对数变好**，两个口径必须一起报 |
| `check_herb_coverage` | 18.2% 会下降（医案里的药更可能查到） |
| 知识块预算 | 本草条目变多，`context_prefix` 的裁剪循环要重新量（SOURCES 第 91 条那个"砍到 1 味"的坑） |
| **不会动的** | 图谱节点、ε、分歧度（都不按本草总数算）、药典两张表 |

**真正的风险不是数量，是把 391 个里的假异写合错**，以及
`herb_not_in_ontology`（revise 级）会因为本体变大而少报——它是防模型编药名的，
本体收了大量冷僻药之后，编出来的名字更可能"碰巧命中"。
建议：扩的时候**只收 452 个"完全没有的"**，391 个存疑的一个不收。

## 三、症状同义词：源不可得，但**问题的大小已经量出来了**

`data/standard/symptom_synonyms.jsonl` 不存在，没做——CMLM 那 27650 条拿不到。

但这一项的判断不该停在"没数据"。现状实测：

- 症状标准词表 = 图里 **1087** 个症状节点；
- S1 之后的匹配是 `_match_graph_symptoms_many` 的**字面双向子串**，
  没有任何同义词层（`syndrome_norm.SYNONYMS` 只有 38 条，且是证候/病机词不是症状）；
- **产品口径**（`tests/queries.txt` 10 条主诉，切成 75 个症状短语）：
  **20 个对不上，27%**；
- 古籍医案口径（1769 种写法）：**65.3% 对不上**——但那是医案原文措辞
  （「倚息不得卧」「下痰水如前」），不是产品输入，不能拿这个数说产品。

**对不上的 20 个里，9 个是脉象与舌象**：脉细弱、脉滑数、脉细数、脉涩、脉缓弱、
脉弦数、舌红少津少苔、舌苔厚腻。而图里含「脉」的节点只有 **10** 个、
含「舌/苔」的 **17** 个，合计 27 个占 1087 的 2.5%。

所以这一项的性价比最高的不是"合 27650 条同义词"，而是
**补一份脉象/舌象标准词表**（28 单脉 + 常见相兼脉 + 舌质舌苔组合，量级几百条），
可以手工整理，不依赖 CMLM。剩下 11 个对不上的是复合描述
（「空腹尤甚」「得食稍缓」「按之不痛」），那属于 S1 该不该把一句话拆成
「症状 + 程度/条件」的设计问题，不是词表问题。

顺带查到：1087 个症状节点里有 **34 个（3.1%）是脏的**——含句号把两个症状粘在
一起（「舌强语骞。平素头晕头痛」）、把引文吞进名字
（「脉弦滑。《金匮要略·妇人杂病脉证并治》载有…」）、含空格（「脉 细」）。
量不大，但清掉是零成本的。

## 四、TCM-MKG：本沙盒下载不了，给不出实测数字

```
$ curl https://zenodo.org/api/records/15395588
CONNECT tunnel failed, response 403
$ curl $HTTPS_PROXY/__agentproxy/status
"host": "zenodo.org:443", "detail": "gateway answered 403 to CONNECT (policy denial)"
```

zenodo.org 与 huggingface.co 都在这个环境的网络策略之外，**不是 TLS 问题、
不能靠改配置绕**。所以"下载多久、解析多久、能补多少味归经"三个数我给不出实测，
只能给推算，并明确标成推算：

- 1.1GB TSV，按 20MB/s 计约 **1 分钟**下载（AutoDL 上）；
- 逐行扫 + 按药名归一，TSV 纯文本 1.1GB 约 **2–4 分钟**（参照本项目读
  9776 行 jsonl 的开销线性外推，不含建索引）；
- 归经能补多少味 **无法推算**：取决于它的药名与我们 1232 味的交集，
  而那正是第一项证明了不能靠猜的东西。

**建议的做法**：不要直接写合并脚本。先在 AutoDL 上跑一个探针——
只读前 10 万行，报出它的列名、药名列的取值样例、以及**与我们 1232 味的交集**，
再决定值不值得全量解析。这跟 R64 的教训一致：R64 先量了"能填多少空槽"
才决定合并哪几个源，没量的那个（CMLM）最后是 0 条。

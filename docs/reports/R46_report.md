# R46 · 临床工作流闭环：从「诊断—方案」补成「采集—诊断—方案—检索—管理」

> **依据**：灵枢云在三甲落地时构建的是「采集—诊断—方案—检索—管理」一体化闭环；
> 它列出的行业痛点第二条就是**病历书写耗时**。此前这个系统只有中间两段。

§7 的 15 项逐条交代在下面。**有一项降级**（循证对照的底本），在 §3 单列并写明
降级到什么、为什么、界面上怎么如实说。

---

## 1. §7.1 采集：结构化四诊 + 「人」这一维

### `core/intake.py`

`IntakeForm` 13 个字段按望闻问切分四组，外加 `PatientProfile`（人维）与
`free_text`（拆不出来的原文）。字段表由 `/api/intake/form` 下发，**前端不写死**
——写死的话这里加一个字段，表单上不会长出来。

| 诊 | 字段 |
|---|---|
| 望 | 舌象、面色、形体 |
| 闻 | 声音、气味 |
| 问 | 主诉、现病史、既往史、饮食、二便、睡眠 |
| 切 | 脉象、腹诊 |

**常用词一键选** 9 组、37 条，全部是教材里的规范写法——表单的价值一半在"快"，
一半在"填进去的是规范术语而不是各写各的"。

### 自由文本仍然是主路径，二者可互转

`form_to_text()` / `text_to_form()`。后者是**尽力而为**：认得出的填进字段，
认不出的留在 `free_text`，一个字都不丢。判据是"形如 `标签：内容` 的片段"，
不做分词、不猜——猜错会把「脉弦」填进面色栏，而那比留在自由文本里糟得多。

### 「人」这一维（对标黄煌的「方—病—人」）

`PatientProfile`：年龄、性别、生理阶段、体质倾向（九种体质的 `Literal`）、
基础病、过敏史、在服药物、肝肾功能不全（**只收有/无/不详三态**）。

**全部字段可空**：门诊现场未必问得全，而一个"必须填满才能辨证"的表单在诊室里
会被绕过去（写个假年龄），那比留空更糟。

### §0.4 输入侧护栏：三层

1. **表单上写着**：`/api/intake/form` 下发一句「只接受文字描述。舌象照片、
   脉诊仪信号、检验数值等客观数据不在本系统的输入范围内」，渲染在表单顶部。
2. **请求边界拦**：`TextOnlyInput` 基类（`ConsultRequest` / `IntakeParseRequest` /
   `IntegrationConsultRequest` 都继承它）对多出来的字段过一遍
   `check_input_kinds()`，命中 7 类禁收输入之一就 400，正文是那句监管属性的
   中文说明——**不是 422 加一串 pydantic 的英文**。
3. **源码级测试**：`tests/test_intake_form.py::test_the_source_has_no_image_or_signal_input_field`
   AST 扫 `core/intake.py` 与 `core/schemas.py` 的字段名，出现
   `image/photo/signal/ecg/imaging/lab_value` 就红。

> 这条护栏不是防御攻击，是**防止有人出于好意加个功能**——"顺手支持传张舌象
> 照片"在工程上是二十行代码，在监管上是换一个产品类别。

## 2. §7.2 诊断与方案：补「人」维

### `core/individualize.py`：确定性计算，零 LLM 调用

**这是对任务书的一处加强，不是降级，理由写在这里。** §7.2 第 3 条说
"`S3Structured` 增加 `patient_profile` 输入与 `individualization` 输出"。
`patient_profile` 确实进了 `consult()` 的签名；但 `individualization`
**不由模型产出**，而是从本体现算——因为 `IndividualizationItem.basis` 是
`Field(min_length=1)`，而让模型生成的话那个字段只能是编的。
**算得出来的东西不问模型。**

| 维度 | 依据来自哪 | 实测条数 |
|---|---|---|
| 妊娠/哺乳 | 本草「禁忌」里提到孕的条目 | **210** 条（《中药学》，禁忌共 820 条） |
| 毒峻药（老年/小儿慎用） | 本草「性味」里标有毒/小毒/大毒 | **225** 条 |
| 儿童剂量折算 | 本草「用量」条目（**900** 条）+ `DOSE_LIMITS` | 按方现查 |
| 肝肾功能不全 | 本草「禁忌」里提到肝/肾的条目 | 按方现查 |
| 过敏史 | 医师填的表单本身 | — |
| **在服西药相互作用** | **本项目没有药物相互作用本体** | **0：不提示，如实记在 `considered` 里** |

最后一行是这个模块最要紧的一条：**取不到依据的维度，不产出条目，但要说
"查过了、没有依据可用"。** 空的 `items` 配上非空的 `considered`，才说得清
"查过了没有需要调的"和"根本没查"的区别。

实测（沙盒）：
```
妊娠期 + [桂枝, 甘草, 细辛] → 1 条慎用提示，依据是《中药学》的「使用注意」原文
老年   + [细辛, 附子]        → 2 条慎用提示（性味带毒），
                              considered 里带"在服西药相互作用：取不到依据即不提示"
空 profile                   → 0 条 + "未填写患者的…信息，本次没有可依据的个体化维度"
```

### 进了 R44 的规则表

新增 `verify_patient_fit`（capability=`verify`，gate=`core.individualize:individualize`）。
**跟 `verify_and_revise` 是两条**：那条验的是"这张方本身立不立得住"（配伍、
剂量、归经），这条验的是"这张方对**这位患者**合不合适"。合成一条的话，
"方是对的但人不对"会被说成方有问题。

## 3. §7.3 循证对照层：**这一项降级了**

### 降级说明（唯一一项）

任务书要的是《中医药循证临床实践指南》的条目。**那份指南的全文不在这个项目里，
也没有可公开获取的机读版本**；照抄一份"指南说什么"等于编造出处，而这个项目
每条结论都要能核对到原文。

按用户的降级指示做**教材推荐方案对照**，底本是 `data/standard/formulary.jsonl`
（《方剂学》，3184 条三元组、235 首方）。

**界面上如实称「与教材推荐方案的对照」，一处不称"指南"**——有一条 Playwright
判据和一条 pytest 判据分别钉住这件事（`BASIS_LABEL` 里不许出现"指南"二字；
渲染出来的文字里出现"指南"即红）。

### `data/standard/guidelines.jsonl`（`offline/build_guidelines.py` 生成）

```
rows              285
syndromes_covered  52 / 337   （15.4%）
formulas          155
books             ["方剂学"]
```

**覆盖率照实报。** 任务书原文希望"初版至少覆盖脾胃门全部证型"，实际是 52 个
证型——差距的来源是：证型 → 方的匹配走的是 `Ontology.formulas_for_syndrome()`
（主治文本里去掉尾「证」后做子串匹配），而 337 条证候里多数的名字不会原样出现
在《方剂学》的主治行里。**没有为了把数字做大而放宽匹配**：放宽的代价是把
不相干的方摆成"教材推荐"，那比覆盖率低糟得多。

每一条都带 `source`（书名）与 `span`（原文片段）；**取不到 span 的条目不收**。

### `core/guideline_compare.py`：三类结果

| 结果 | 含义 |
|---|---|
| `covered=False` + `not_covered` | 底本里没有这个证型。**如实说，不编**，并写明"不代表推导有误，也不代表它被教材支持" |
| `aligned` | 一致的部分（主方/治法/加减），每条带出处 |
| `deviations` | 不一致的部分，含「教材推荐什么、本次是什么、差在哪」 |

- **治法比对走 `core.effect_synonyms.expand_effect`**，不裸比字符串——
  覆盖检查那次撞墙（「水肿」vs「肿胀」）就是裸比出来的。
- **加减只在主方一致时才算**：方都不一样，比药味差几味没有意义。
- **这一层不参与选择**：没有分数、没有排序、不回答"哪个更好"——那会把它
  变成另一种投票（R44 刚把投票痕迹从产品面消除）。有一条测试扫模块里的
  全部符号名，出现 `score`/`rank`/`best`/`prefer`/`choose` 即红。

## 4. §7.4 病历文书自动生成

### `core/emr_writer.py`

字段对齐国家中医药管理局《中医病历书写基本规范》：主诉 / 现病史 / 既往史 /
过敏史 / 四诊摘要 / 中医诊断（疾病 + 证候）/ **辨证分析** / 治法 / 处方 /
医嘱 / 医师签名栏 / 日期（循证对照在场时多一段）。

**辨证分析那一段直接来自推导链**（病位、病性、病机、推导过程）——这是本系统
最有价值的输出，也是医师手写时最费时间的一段。

### 三种导出，一个来源

| 导出 | 用途 | 要点 |
|---|---|---|
| `render_emr_text()` | 粘进 HIS 的病历编辑器 | **纯文本、不带 markdown 记号**——HIS 编辑器多半不认，粘进去会留下一堆井号和星号 |
| `render_prescription_sheet()` | A4 处方笺 | 药材那一段**复用 `core.prescription.format_pharmacy_text`**，不另写一套对齐逻辑 |
| `EMRDraft.model_dump()` | HIS 接口导入 | 字段命名与 §7.5 的接口一致 |

三种导出**都带**「本文书为辅助生成的草稿，须经执业医师审核修改后方可作为
正式病历」与用途声明。

### 医师编辑留痕

`apply_edits()` 逐段比对并返回**改前改后**，`record_edits()` 写进审计链
（`kind="emr_edit"`）。只写改后的话，"医师把哪一句删了"就查不出来，而那正是
质控要看的。不可编辑的段（签名栏、循证对照）收到修改时**明确拒绝并记一条**，
不是静默丢弃——静默丢弃会让医师以为自己改了，而导出的还是原文。

### §0.4 合规措辞

文书里不出现"建议患者服用 X"这类指向具体患者的诊疗建议。有两条测试：
一条扫三种导出的成品文本，一条 AST 扫模块的字符串常量（**摘掉文档字符串**
——那里正写着"不得出现『建议患者服用』"）。
**就医指引不在红线内**：「建议尽快就诊消化内科」照旧，它说的是去哪里，
不是吃什么。

## 5. §7.5 检索与管理

### 知识速查（`core/knowledge_panel.py`）

四类：本草 / 方剂 / 教材推荐方案 / 名老中医用药规律。**四类分开摆，不融合**
——融合会让"我明明在查药"变成"返回了三条医案"。

前端 Ctrl/⌘ + K 唤起。实测：

```
冷启动（含本体装载）  2408 ms
热查                     4 ms      预算 200 ms ✅
```

冷启动那一次在生产部署里由 `api/warmup.py` 在起服务时吃掉，医师遇不到。
这一点写在测试里（先预热再计时）而不是藏起来。

**不调模型**：任何一次模型调用都到不了 200 ms。有一条测试 AST 扫模块里
不许出现 `get_llm` / `generate`。

### 管理（`core/history.py`）

一份 JSONL 追加写，**不引数据库**（CLAUDE.md：demo 阶段不要加数据库）。

- **历史**：按医师/证型/方剂/日期检索，最新在前。只记摘要与编号，
  完整轨迹按 `record_id` 回审计链——两处各存一份会让"改了哪一份才算数"没有答案。
- **收藏与模板**：医师收藏常用方 + 自己的批注。
- **统计**：近 N 次的证型分布、常用方、核查提示分布。**每个数都带
  `of`（这批一共几次）**——「肝胃不和证 3 次」在 5 次里和在 50 次里是两件
  完全不同的事。措辞里写明"给自己看的用药习惯回顾，不是考核指标——不排名、
  不跟别人比、也不算正确率"：一个会被拿去考核的统计，医师会开始为它而开方。

半行 JSON（写到一半掉电）跳过那一行，**不让整份历史读不出来**。

### HIS 集成接口（`core/integration_auth.py` + 两个端点）

| 端点 | 作用 |
|---|---|
| `POST /api/integration/consult` | HIS 传患者基本信息与主诉，返回结构化结果 |
| `GET /api/integration/emr/{record_id}` | 返回病历文书结构化 JSON |

- **OpenAPI 3**：`app.openapi()` 里两条路径都在，`info.title`/`version`
  出自 `core/version.py`。
- 请求字段对齐常用 HIS 术语：`patient_id`（患者主索引）、`visit_id`（就诊流水号）、
  `chief_complaint`、`present_illness`。
- **鉴权 = API Key + IP 白名单**（等保 2.0 三级的身份鉴别与访问控制）：
  - **默认拒绝**——没配 `HIS_API_KEYS` 时一律 401。一个默认放行的鉴权在内网里
    等于没有鉴权，而医院内网并不比公网干净。
  - key 比较用 `secrets.compare_digest`：`==` 是短路比较，逐字节的耗时差可以
    被用来把 key 试出来。
  - **IP 白名单为空 = 不限 IP**（跟 key 方向相反）：强制配置会让人填一个
    `0.0.0.0/0` 了事，那比不配更糟——它看起来像配过了。
  - 回给调用方的原因**统一**为「鉴权失败。」——"key 不对"和"IP 不在白名单"
    的区别会告诉试探者下一步该试什么。

## 8. 无法完成项

**只有一项，且已按用户指示降级，不是省略：**

> **§7.3 第 5 条「`guidelines.jsonl` 收录《中医药循证临床实践指南》条目」**
> → 降级为「教材推荐方案对照」，底本《方剂学》，285 条、覆盖 52/337 证型。
> 界面文案如实称「与教材推荐方案的对照」。
> **将来拿到指南全文时**：那个文件多一批 `source` 不同的行即可，
> `core/guideline_compare.py` 一行不用改（`evidence_level` 已经预留成一个
> 可扩展的值，不是写死的布尔）。

另外两处需要说清口径、**不是降级**：

1. **`individualization` 由确定性计算产出，不由模型产出**（见 §2），
   这是加强不是削弱。
2. **覆盖率 15.4% 照实报**，没有为了把数字做大而放宽证型匹配。

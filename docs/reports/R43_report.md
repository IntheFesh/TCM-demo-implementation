# R43：全站交互延迟治理

> 本轮最重要的一条不是某个数字变小了，是**发现原来的量法会得出错误结论**：
> 把 INP 拆成三段之后，全站 12 个交互的「处理」段都是 ~0 ms——因为这个应用的
> 点击处理函数都是立刻返回的，真正的等待发生在 await 之后，**落在 INP 的观测
> 窗口之外**。光看 INP 会说"一点延迟都没有"，而用户明明在等。

## 1. 量法：为什么 INP 一个数不够

### 1.1 三段口径

用 `PerformanceObserver({ type: "event", durationThreshold: 16, buffered: true })`
收 `PerformanceEventTiming`，每次交互拆成：

```
input delay   = processingStart - startTime        事件排队等主线程
processing    = processingEnd   - processingStart  事件处理函数本身
presentation  = startTime + duration - processingEnd  处理完到下一帧画出来
```

**三段的修法完全不同**：输入延迟慢 → 主线程上有长任务，要切片或挪 Worker；
处理慢 → 那个函数太重；呈现慢 → 改了太多 DOM、或者强制同步布局。
报一个总数，没人知道该改哪一处。

### 1.2 输入必须是可信的

R41 的 `measureInteraction` 用 `el.click()`。那是**不可信事件**，不进
`PerformanceEventTiming`——量不到真实的输入延迟。R41 在 CLS 那条上已经踩过
同一个坑（`hadRecentInput` 的 500 ms 窗口只认可信事件）。所以这一轮全部走
Playwright 的真实鼠标/键盘。

### 1.3 实测结果：INP 全站合格，但它没回答"等了多久"

12 个交互，INP 中位数 16–56 ms，**全部在预算内**：

| 交互 | INP 中位 | 输入延迟 | 处理 | 呈现 | 上限 |
|---|---|---|---|---|---|
| 切页签 | 16 | 0.4 | 0.1 | 15.6 | 100 |
| 点示例主诉 | 16 | 0.3 | 0.2 | 15.5 | 100 |
| 连打 20 个字 | 16 | 0.0 | 0.0 | 16.0 | 100 |
| 展开/折叠九段的一段 | 16 | 0.3 | 0.1 | 15.6 | 100 |
| 点图上一个节点 | 24 | 0.9 | 0.1 | 23.0 | 200 |
| 重播生长动画 | 16 | 0.3 | 0.2 | 15.5 | 200 |
| 导出 PNG | 32 | 0.4 | 0.2 | 31.4 | 200 |
| 切换角色（自绘下拉） | 16 | 0.4 | 0.2 | 15.4 | 100 |
| 图谱浏览器：展开一个证素 | 24 | 1.6 | 0.0 | 22.3 | 200 |
| 图谱浏览器：搜「痛」 | 56 | 0.5 | 0.2 | 55.3 | 200 |
| 图谱浏览器：连展开 5 个后再展 | 24 | 1.9 | 0.0 | 22.1 | 200 |
| 图谱浏览器：重置视图 | 16 | 0.4 | 0.2 | 15.5 | 200 |

**`处理` 那一列全是 ~0。** 16 ms 基本就是"一帧"——也就是说这些数字量到的是
"浏览器画下一帧要多久"，不是"这件事要多久"。真正的工作在 await 之后。

### 1.4 所以加第二个数：settle（点到结果出现）

从 `pointerdown` 打点（**不用 click**：click 在鼠标抬起后才派发，中间那
~50 ms 是按下-抬起的间隔，不该算进等待），等到一个页面上的条件成立为止。

| 交互 | settle 中位 | 上限 | 说明 |
|---|---|---|---|
| 切到图谱页签（**冷态**） | **151 ms** | 1000 | 拉全量证素 + 建索引 + 首次布局 |
| 图谱浏览器：搜「痛」 | **98 ms** | 1000 | 服务端搜 + 合并 + 重排 |
| 图谱浏览器：连展开 5 个后再展 | **36 ms** | 1000 | 合并与索引的累积成本在这里才看得出来 |
| 点图上一个节点（tooltip 钉住） | **13 ms** | 1000 | 纯前端 |

**上限 1000 ms 的来处**：Nielsen 的三档阈值——0.1 秒=瞬时、**1 秒=思路不被
打断**、10 秒=注意力流失。INP 的 200 ms 同理来自 Core Web Vitals 的 "good"
阈值。两个都是外部基准，**不是自己拍的数**——自己定一个宽松的数然后宣布达标，
那个数就没有意义。

### 1.5 量具自己的两个 bug（都会让数字说谎）

1. **切页签的 settle 一开始量出来是 9 ms。** 因为第二次重复时数据已经在内存里，
   `gbCy.nodes().length > 0` 立刻成立——那 9 ms 什么都没等。
   **报一个"什么都没等"的数比不报更糟。** 改成只量第一次（冷态）并标注。
2. **点图上节点的 settle 一直超时。** 图在折叠区里、位置很靠下，
   `getBoundingClientRect()` 给的是视口坐标，`mouse.click` 点到了页面外——
   表现是"交互做了但什么都没发生"，跟"功能坏了"长得一模一样。
   改成先 `scrollIntoView` 并断言画布真的在视口里。

## 2. 压缩：本轮最大的一笔

### 2.1 实测：一个字节都没压

```
/api/graph?limit=200            351,979 B   content-encoding: (无)
/api/graph/search?q=痛&limit=150 21,848 B   content-encoding: (无)
/app/graph.js                   145,416 B   content-encoding: (无)
```

点开「图谱」页签拉的就是第一条。**352 KB 未压缩**，而 JSON 正是压缩率最高的
那一类数据——实测这份载荷的 gzip 压缩率是 **4.5%**（压完只剩 4.5%）。

| 端点 | 改前（上线字节） | 改后 | 变化 |
|---|---|---|---|
| `/api/graph?limit=200` | 351,979 | **16,000** | **−95.5%** |
| `/api/graph/search?q=痛&limit=150` | 21,848 | **3,596** | **−83.6%** |

### 2.2 但不能无脑全开：两类必须跳过

1. **SSE（`/api/consult/stream`）。** starlette 的 `GZipMiddleware` 对流式响应是
   逐块写进 gzip 缓冲再发，而 gzip 在攒够一个块之前不产出任何字节——
   "一边推理一边出字"会变成"憋一会儿吐一大段"。**R36 花了一整轮把流式做出来，
   不能在这里被压缩缓冲抵消掉。**
2. **已经压过的二进制**（woff2 / png / jpg / webp）。再压一遍省不下几个字节，
   却要为每个请求付一次 CPU。字体那 1.13 MB 是首屏的大头（R41 实测占 77.7%），
   白烧 CPU 会直接体现在首屏时间上。

判据按**路径**定而不是按 content-type：中间件要在响应头出来之前决定走不走压缩，
按路径是确定的、可测的，而这两条规则本来就跟路径一一对应。

压缩本身**复用 starlette 的实现**——自己写一遍 gzip 响应器就是同一件事的第二处
实现（判据：`SelectiveGZipMiddleware` 的源码里不许出现 `zlib`/`gzip.compress`）。

### 2.3 不为性能牺牲正确性

判据里有一条 `test_compression_does_not_change_the_bytes`：压完解开必须跟不压
的响应**逐字节相同**，JSON 也要相等。另有一条钉住"客户端不支持 gzip 时照样拿到
合法响应"。

### 2.4 一个做了测量之后**决定不做**的优化

原本打算做"边字段的值表压缩"：`/api/graph` 的 787 条边里，
`lambda1_by_physician` 只有 **2 个**不同的取值（全 0 的那张表，或 null）却占
81.5 KB，`weight_by_physician` 只有 **3 个**取值却占 80.8 KB——两者合计是载荷的
**47%**，而携带的信息不到 800 bit。

**测完决定不做**：gzip 已经把这份载荷压到 4.5%，值表能省的那部分几乎全被 gzip
吃掉了，而它要改变线上的数据形状（每条边多一个索引字段、前端要在一处展开），
**收益不明、复杂度确定**。先测量后优化那条规矩在这里给出的答案是"不优化"。
这个发现记在这里，等载荷形状将来真的成为瓶颈时可以直接拿来用。

## 3. 点击处理里不许有随规模增长的重活

`gbMergeGraph` 每次合并都 `new Set(gbGraphData.graph.edges.map(e => e.data.id))`
——O(已累积的边数)，而一次浏览会合并很多次（首屏、每次展开、每次搜索），
合起来是 O(边数 × 合并次数)。

**规模是真的**：本沙盒的持久图是 **2356 节点 / 3682 边 / 2.55 MB**，
教材扩完还要翻几倍（证候 337 → 1444、症状 1282 → 约 7000）。
**而这段代码跑在点击的处理函数里**——正是 INP 的 `processing` 那一段。

改法：边 id 的集合跟着 `gbIndex` 一起长期留着，合并时只加新的。
实测 `browser_expand_repeat`（连展开 5 个证素之后再展一个）settle 36 ms，
`browser_expand`（第一次展开）22–24 ms——**累积成本没有随次数放大**。

## 4. 「点了没反应」：把等待说出来

这个项目一直在防"静默失败"。R43 发现同一类问题的另一副面孔：**静默等待**。

- `gbFetchInto`（搜索 / 展开 / 切图层）**要等响应回来才改状态栏**。在三甲内网上
  点「搜索」之后按钮看起来是死的。
- `openNodeExplain` **要等响应回来面板才出现**。点一个节点之后屏幕上什么都不变，
  人会以为点漏了再点一下（于是又发一次请求）。

改法：

- 点下去**立刻**写状态：「搜索中…」/「展开中…」/「切换图层中…」
  ——**说清在做什么，不写一个笼统的「加载中」**：这几件事的耗时差一个量级，
  人只有知道在等什么才知道该不该继续等。
- 超过 **300 ms** 才把文案升一级（「这张图比较大，稍候」）。
  300 ms 以下的等待人感觉不到，弹一个转圈反而制造"刚才是不是卡了"的印象。
- 释义面板先摆一个**带节点名**的骨架，**不是一个转圈图标**——它能立刻说出
  "正在查哪个节点"，人据此确认自己点对了。
- 两处都带 `aria-busy`，读屏软件知道这一块还在变。
- 顺带补上 `gbFetchSeq`：**连点两次搜索时，先回来的那个不该覆盖后点的那次的
  状态文案**——跟 `openNodeExplain` 的 `NODE_EXPLAIN_SEQ` 是同一类竞态的另一个
  入口，两处都得有。

## 5. 服务端交互端点：预算与实测

「人点一下就会发的请求」（不含 `/api/consult`，那是几十秒的推理，R40 单独治过）：

| 端点 | 中位 | 上限 |
|---|---|---|
| `/api/graph?limit=200` | 22.7 ms | 150 |
| `/api/graph?node_types=syndrome&limit=200` | 18.2 ms | 150 |
| `/api/graph/search?q=痛&limit=150` | 5.7 ms | 150 |
| `/api/graph/neighbors?node=element::肝&limit=150` | 7.4 ms | 150 |
| `/api/node_explain`（药材） | 12.3 ms | **50**（R42 定的，这一轮再钉一遍） |
| `/api/node_explain`（证型） | 9.6 ms | 50 |

R42 那条 50 ms 的预算在这一轮**重新验了一次**，理由是：R43 给每个响应都加了一层
压缩中间件，**加中间件不许把既有预算吃掉**。

## 一、这一层跟既有两层的分界（第 31 条）

| 层 | 回答的问题 | 产出 | 动作 |
|---|---|---|---|
| `core/safety_output.py` | 这方能不能**发出去** | `FormulaSafety` | 拦截 |
| `core/formula_check.py` | 这方**拟得好不好** | `Advice` | 建议 |
| **`core/formula_verifier.py`** | 这方的每一条主张在**本体里站不站得住** | `Violation` / `Unverifiable` | **回灌重开** |

前两层判的是方本身；这一层判的是**方与它声称的依据之间的关系**。

**`incompatible_pair` 与 `dose_exceeds` 两条规则完全委托给 `safety_output`**
——验证器不持第二份配伍表、不排第二套查表顺序（有源码级测试断言
`INCOMPATIBLE_PAIRS = ` 不出现在验证器里，24 对配伍逐对验过都能被查出来）。
它加的只是**本体那一层的反例**：

```
甘草 与 甘遂 属配伍禁忌（甘草-甘遂），同方相见不可下发
依据：【使用注意】不宜与海藻、京大戟、红大戟、甘遂、荒花同用。……
      ；【使用注意】孕妇及虚弱者禁用。不宜与甘草同用。
```

**structured 模式因此只有一条重开路径。** legacy 那条"安全层拦截 → 重开一次"
在 structured 下被验证器取代（有测试断言 `run_synthesis` 里不再出现
`format_blocking_issues`，也不再有第二处 `get_llm().generate(`）——两个循环各自
决定"要不要重开"的话，同一张方可能被改两遍，而 `llm_calls` 是额度结算的依据。

## 二、34a：查不到依据 ≠ 查到了且通过

**这是本轮最要紧的一条，也是差点做错的一条。**

七条规则里四条要查本体。药理层数据的缺谓词分布是实测的：

| 谓词 | 缺的条数 | 占 1232 味 |
|---|---|---|
| 归经 | 598 | **49%** |
| 用量 | 672 | **55%** |
| 禁忌 | 770 | 63% |
| 炮制 | 790 | 64% |
| 性味 | 189 | 15% |
| 功效 | 49 | 4% |

第一版 `passed` 只看"有没有违规"。拿 `cases.json` 里 **80 张真实医案方**跑一遍：

| `passed` 的定义 | 结果 |
|---|---|
| 只看违规（第一版） | **68 张（85%）"已验证通过"** |
| 无 veto + 无 revise + **unverifiable 为空**（改后） | partially_verified **68** / revise_needed **10** / vetoed **2** |

同一批里有 **854 处判不了**（`herb_grounded` 513、`meridian_coverage` 141、
`nature_conflict` 80、`effect_matches_method` 120）。
"85% 通过"和"85% 没能验全"这两句话对读者的意义完全相反。

做法：新增 `Unverifiable(rule, herbs, missing_predicate, reason)`，
`status` 多一档 `partially_verified`。两条配套判据：

1. **一条规则"跑了但判不了"时不许记进 `checked_rules`**
   ——`checked_rules` 是"真的判了哪几条"，它和 `unverifiable` 一起才是完整的账。
2. **一味药都判不了的时候不出违规**（`meridian_coverage` / `effect_matches_method`）
   ——那时"没覆盖"只是"不知道"，报一条违规会让模型去改一个本来可能对的方。

`reason` 是一句完整的话而不是代号，因为前端与报告要**原样显示**：

> 本体里「鲤鱼」这味药没有（本草 1232 味覆盖不到它），它的功效依据无法核实
> ——这是药理层覆盖不全，不是模型编造

**本体整个不可用时七条全部进 `unverifiable`**，不是全部通过：
那句"符号验证通过"在没有本体的环境里会恒真，而它恒真时毫无意义。

### `herb_grounded` 判的是"编造出处"，不是"这味药不在本体里"

这是 34a 的同一条洞见用在规则设计上。实测本体只覆盖医案药名的 **39.8%**，
把"不在本体里"当 veto 几乎每张方都会被否掉——而那不是模型的错。所以：

| 情况 | 判定 |
|---|---|
| 引用的 `span` 在本体该 (药名, 谓词) 下找不到 | **veto**（编造出处） |
| 这味药本体里根本没有 | `Unverifiable`（数据缺） |
| 这味药在本体里但一条 `ref` 都没给 | `Unverifiable`（没引，不算编造） |
| 引了一个本体里没有的谓词 | `Unverifiable`（对不了） |

`span` 用**双向子串**比而不是相等：本体原文往往是一整段，模型照抄时可能只抄一句，
要求逐字相等会把正确的引用判成编造（三种抄法各验一条）。

## 三、闭环：三轮、关思考、残余分级

```
验 → 有 violations 且轮数未满 → 带反例重开（thinking=disabled）→ 再验 → …
```

三条设计决定，各有测试：

**一、重开关思考。** 这一步不是"再想一遍怎么辨证"（证型、治法、五步链都定了），
是"把这味药换成归肝经的"这种照着反例改的局部修补。开思考在这一步是纯浪费
（§0.4 实测单次 S3 开思考 260–479 秒），而且更容易把已经对的部分想坏。
测试断言首轮 `thinking != "disabled"`、重开那次 `== "disabled"`。

**二、残余分级。**

| 残余 | 后果 |
|---|---|
| veto 级 | 抛 `SymbolicVeto`，**整次问诊不产出方药** |
| revise 级 | **照常下发**并如实标在 `verification` 里 |

revise 残余压着不发等于因为一条归经覆盖建议就不给患者任何东西。

**`SymbolicVeto` 跟 `SafetyVeto` 是两个异常**，不是复用一个：前者是输出侧
（方有配伍禁忌/超量/编造出处），后者是输入侧（主诉里有危重症状）。
合并之后患者分不出是"你该立刻就医"还是"系统改不出一张合规的方"——
这两件事该做的完全不同。`safety_flag` 也不复用，veto 原因在自己的
`verification_veto` 字段里。

**三、每轮的结果都留着。** `verifier_first_pass_rate` 要的是**第一轮**的状态，
而"改了三轮才过"和"一次就过"在最终态上看起来一模一样。

**`unverifiable` 不进回灌文本**：本体缺数据时模型改方也改不出数据来，
写进去只会让它以为自己错了、去改一个本来可能对的地方。

`MAX_REVISE_ROUNDS=0` 关掉闭环（R38 的消融要拿它当对照组），
实测 `llm_calls` 从 6 降到 3。

## 四、34b：两个分母，差 2 倍以上

| 指标 | 分子 / 分母 | 值 | 是什么 |
|---|---|---|---|
| `herbs_grounded_ratio` | 有本体引用的药味 / **这张方的药味数** | 随方而变 | **模型指标** |
| `ontology_coverage_of_corpus`（按种数） | 230 / **578** 医案药名 | **39.8%** | **数据指标** |
| 同上（按次数） | 3380 / **4799** 次 | **70.4%** | 同上 |
| 本体规模 | — / 1232 | — | **不是上面任何一个的分母** |

拿 1232 当 `herbs_grounded_ratio` 的分母算出来的数毫无意义（它回答"本体里有多少味
药被这张方用到了"，恒接近 0）。两个覆盖率必须都报：只报 39.8% 会低估它对真实
问诊的支撑（常用药覆盖得好），只报 70.4% 会掩盖长尾缺口（古籍特有写法大面积缺）。

两个函数**相邻定义在同一个模块**、各自 docstring 第一段写明分母，
另有一条测试断言两个分母不相等。manifest 里也分两处：
`ontology.corpus_coverage`（数据）与 `synthesis.herbs_grounded_ratio`
（模型，带 `herbs_grounded_denominator: "本次方的药味数"` 一栏）。

**缺谓词计数一起进 manifest**：引用"符号验证通过"的人必须能同时看到
"验证依据的那份本体缺了一半归经"。这件事不在同一个地方出现，那句话就会被当成
"全验过了"。

## 五、34c：235 首方查清了，两个假设都不成立

任务书给了两个假设，实测**都不成立**：

| 假设 | 实测 |
|---|---|
| 方名归一把不同方并到一起了 | 名字里有两个方剂后缀的只有 **3** 条，都是正常长方名（麻黄杏仁甘草石膏汤 / 竹叶石膏汤 / 大黄牡丹汤） |
| 抽取时方名带了章节前缀 | 含数字或章节标记的 **0** 条 |

真正的证据是：**3184 条三元组一条不丢地归到 235 首方**（有测试逐条核）。
谓词只有 8 种：功用 235、组成 234、主治 234、君药 182、臣药 175、佐药 173、
使药 115、加减 34。

所以 **235 是源文本里就这些方**，不是归并丢了东西。《方剂学》教材的正方数量约
200 出头，235 在合理范围。

**方名形态实测的一个真问题**：少数名字被 OCR 截短——
「桑散」（桑螵蛸散/桑白皮散）、「大秦汤」（大秦艽汤）、「人参蛤散」（人参蛤蚧散）、
「加减葳汤」（加减葳蕤汤）。名字 ≤3 字的有 **113** 条，其中绝大多数是正常短方名
（一贯煎、二陈汤、四物汤……），截短的是少数。这会让
`Ontology.formula("人参蛤蚧散")` 按标准方名查不到它。

**按 34c 的要求：只报数、不改。** 改方名归一会动 235 这个已测量的数，
而 R38 的消融若依赖方剂本体就不可比。有一条测试把 235 / 1232 两个数钉住，
改它必须连同 R38 的可比性说明一起更新。

**R38 的已知限制（写在这里，R38 报告要引）**：方剂本体 235 首、少数方名 OCR 截短，
按标准方名查询会漏；消融实验中凡依赖 `formulas_for_syndrome` /
`Ontology.formula` 的部分都要标这条。

## 六、顺带量出并修掉的三个缺陷

### 6.1 一个缓存缺失，数据一进来就变成每请求 300 ms（快了 2.6×）

`build_entry_index(kind)` 读并索引药理层三元组，**没有缓存**。数据不在时
`_load_triples` 恒返回空，建索引不花时间；数据一进来（9776 + 3184 条），
建一次 **41 ms**，而它一次问诊被调**四处**（`materia_index` / `build_shared_prefix`
109 KB 文本 / `build_entries_section` / 本体构造），每位医家各一遍。
另加 `get_ontology()` 首次 **2057 ms**，也在第一个请求里惰性触发。

**没有任何测试会因为"变慢了"而红。** 先红的是那条测**并发**的计时测试
（`0.3 × 3 × 0.7 = 0.63s` 的时限被顶破）——一条计时测试在测别的东西时抓到了
一个性能回归。

修了三处，实测 **1.005s → 0.385s（2.6×）**：
缓存加在 `build_entry_index` **这一处**（不是四个调用方各加一层——那样清缓存要
清四处，漏一处就读到脏数据）；`_warmup` 预热本体层；那条并发测试显式预热本体
再计时，并写清**不许靠放宽时限来"修"它**（那会把真实的冷启动开销藏起来）。

缓存两条硬约束：**传了自带数据的那一路不碰缓存**（否则下一个无参调用读到别人的表）、
**空结果不缓存**（文件可能在进程起来之后才生成）。

### 6.2 路径回退把「显式覆盖」静默吃掉

`core/tools.py::_materia_medica_path()` 的回退分支做的正是它自己文档字符串
上一段警告的事："覆盖失效不报错，只是静默读了另一份文件，最难查的一类"。
测试模拟"数据还没生成"的办法就是把常量覆盖成不存在的路径，而回退会找到真文件。

修法：记下 import 时的原值，**当前值跟它不同就是有人显式覆盖了** → 只认覆盖值。
判据：一个"可被覆盖"的值，必须能区分「覆盖成一个不存在的东西」和
「没被覆盖且那个东西不存在」。

### 6.3 手抄的数字第四次漂

`eval/RESULTS.md` 记的「本草 10248 条 / 方剂 3737 条」是**手抄**的（同一行自己
标着 ⏳）。数据进版本控制后第一次可核：实测 **9776 / 3184**，少 472 / 553 条。
原因查清了：落盘这份是 `c9ac580` 关思考模式重跑的**另一次抽取**，不是同一批
——不是数据丢了。

这一条的价值在于**它证明那套凭据机制有效**：RESULTS.md 当初预言"文件一进来
凭据键就自动生效"，而它真的在第一次 `--check` 里就把手抄值指了出来。
前三次漂都是靠人回头核才发现的。

## 八、也核过了、但这一轮**没动**

1. **`nature_conflict` 在 80 张真实方上一次都没判成**（全部 `unverifiable`）。
   根因：`check_thermal_consistency` 按**证型名的字面**判寒热方向，而 `cases.json`
   里的证型多为「胃阳虚」「悬饮」「关格」这类古籍用词，不含"寒/热/阴虚/阳虚"字样。
   这条规则要真的生效，得先有证型名到寒热方向的映射——那是新一张表，
   **不在本轮范围**，而且要带对照（新表覆盖多少个证型）。
2. **用药规律 0 条**（`patterns_for` 恒返回空）。那是 R35 的产物。
3. **少数方名被 OCR 截短**（第五节）。按 34c 的要求只报不改。
4. **`ontology_coverage_of_corpus` 每次 manifest 都重算一遍**（读 1MB `cases.json`，
   实测 52 ms）。它是**静态数据**的属性，一次问诊里不会变。留到 R36 跟其他
   请求路径上的浪费一起处理（那一轮的题目就是这个）。
5. **验证器只验 `formula.candidate`，没验 `herb_choices` 的 `for_element` 是否
   真的对应本体里那味药的功效**。schema 的 `_no_step_skipping` 只保证
   `for_element` 在"脏腑 ∪ targets"里，没保证"这味药真的能治这条病机"。
   要验它得有"病机 → 功效"的映射，跟第 1 条是同一类缺口。

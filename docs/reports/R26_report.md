## 三、那笔账（这一节是本轮报告的重点）

### 3.1 8000 条要多少钱

估算模型（`estimate_cost()`，零调用）：

| 项 | 数 | 来历 |
|---|---|---|
| 样本 | 8000 条 | 总纲 R26：社区那套「8000 条把 V4 蒸进 9B」的配方 |
| 每条的调用数 | 5 | `calls_per_consult(3 位医家, best_of_n=1)` = 2 + 3×1 |
| 其中 S3 调用 | 3 | 每位医家一次 |
| 每次 S3 的输入 | ~180K token 前缀（**命中**）+ 主诉/S1/S2（未命中） | R21 的 `budget_plan()`，单医家 ≈180K |
| 每次 S3 的输出 | 3600 token（**假设**） | R21 报告里可见输出 ≈1.2K × `effort=max` 下思考 token 的经验倍数 3 |
| 前缀预热 | 540K token 按未命中价付**一次** | 前缀缓存的全部意义 |

结果：**高峰 ¥3,956 / 谷段 ¥1,978**，调用 40,000 次。
`¥40` 预算按高峰价买得起 **70** 条（谷段口径 151 条）。**差 99 倍。**

### 3.2 为什么会差这么多——两件事叠起来

1. **R21**：知识不走检索走前缀缓存。一次问诊便宜（命中价便宜 30 倍），
   但"便宜"的对象是**每次调用都要带的 18 万 token**，不是零。
2. **R22**：S3 在 `full_context` 下开 `thinking` + `effort=max`。
   **思考 token 按输出价计费**（$3.96/M，是命中输入价的 90 倍）。

每条样本按高峰价 ≈ ¥0.49，其中输出 ¥0.31、命中输入 ¥0.17。
8000 × ¥0.49 ≈ ¥3,956。

### 3.3 顺手核出总纲 §1 的 ¥0.17/问诊只算了输入

§1 写「三位医家每次问诊 ≈¥0.17」。核一遍：
540,000 × $0.044/M × 7.2 = **¥0.171**——一分不差。
所以那个数确定是"命中输入"这一项，**没有包含输出**。R22 之后输出那部分是 ¥0.31，
比输入还大。`eval/RESULTS.md` 第 16 行已按「输入 ¥0.17 + 输出 ≈¥0.31」改写。

**一个对得上的数不等于一个完整的数。** ¥0.17 完全正确，它只是账单的三分之一
——这句话比那个数字本身重要，因为同一个形状会在任何"单价 × 次数"的估算里重现。

### 3.4 脚本的默认行为因此是「预算决定规模」

`--limit` 不传时由 `max_samples_for_budget()` 现算。为什么不只放两道闸门：
闸门只回答"太贵了"，人接着要问的是"那能跑多少条"，而后者才是决定。
没有这个函数，人只能拿 `--limit` 反复试——**那是让人去做二分查找**。

三档闸门（`gate()`）：

| 估价 | 行为 | 依据 |
|---|---|---|
| ≤ ¥30 | 直接跑 | §0.5 第 2 条第三款那条线以内 |
| ¥30 ~ 预算 | 要 `--yes-spend` | 「超 ¥30 停一次问、默认跑」 |
| > 预算（默认 ¥40） | **一律不跑**，提示用 `--limit` | 那不是确认一下能解决的事 |
| 算不出前缀大小 | **不跑** | 那时估价是 0，"0 < 30 所以放行"是最坏的一种通过 |

闸门看**高峰价**：谷段五折是可以选的，高峰价是保证不会超过的那个数。

## 七、发现但未动 / 发现并当场修了

1. **当场修了：总纲 §1 的 ¥0.17/问诊只算了输入**（第 3.3 节）。
   `eval/RESULTS.md` 第 16 行已按「输入 + 输出」改写。
2. **当场修了：上机剧本那句「全部跑完 ≈¥X」是个下限，不是上限。**
   均价 ¥0.0055/次是 top3 时代量出来的（一次调用带三条医案），
   而段 9/10 每次调用贵一个量级（段 10 自己的估算器报 ¥0.11/次，**20 倍**）。
   剧本现在明说这个总数是下限，并要求按段问它自己的估算器。
   **未动的部分**：没有给每段都配一个真实估价器——那要每段都有自己的
   token 模型，属于另一轮的事。现在的处理是"明说它不准、指出该问谁"。
3. **发现但未动：`bench_sandbox --all` 在 pytest 红的时候照样写快照。**
   R25 报告第七节记过这个形状，这一轮又用到了（写报告前先跑一次确认全绿）。
   仍然没动它，理由不变：改它属于流水线改造。但这一轮多了一个判断依据——
   R25 那次事故的代价是"一份红的测量成了本轮凭据"，而**一次手工 `git checkout`
   就能恢复**，所以它的优先级低于任何会改契约的改动。
4. **发现但未动：蒸馏样本里医案那一半的"教师抄自己语料"无法在沙盒里量化。**
   要量它得比较教师输出与原案的重合度（真跑之后才有数据）。
   现在的处理是打标（`teacher_saw_source_case`）+ 在 schema 文档字符串和
   SOURCES 第 69 条里写明"下游必须分开统计"。
5. **发现但未动：`OUT_TOKENS_PER_CALL_ESTIMATE = 3600` 是整份估算里唯一的假设。**
   它直接决定 ¥3,956 这个数（输出占 63%）。真机第一批跑完要按实测替掉
   （第六节第 5 项）。脚本里标了「这是假设不是实测」，测试钉住这句话在。

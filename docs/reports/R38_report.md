## 一、四组：一组只动一个开关

| 组 | 开关 | 回答什么 | 调用数（沙盒实测） |
|---|---|---|---|
| A | （产品默认） | 基线 | **3** |
| B | `S3_MODE=legacy` | 五家融合成一条链 vs 三家各说各的 | **5** |
| C | `S3_BEST_OF_N=3` | 采三次挑最好的那次，值不值三倍的钱 | **5** |
| D | `S1S2_MERGED=1` | 省一次往返的代价 | **2** |

调用数这一列**现在就能读**：它是结构性的（S1/S2 段 + S3 段），跟模型给什么内容
无关。三指标那几列要真实 LLM。

**D 组只在消融里开。** 合一会把证素推断挪到安全否决之前（CLAUDE.md 那条铁律，
理由见 SOURCES 第 93 条），所以产品里默认关着。这一组量的是"关着它损失了多少"，
不是"要不要打开"——后一个问题的答案已经是"不打开"。

**串味是消融里最难查的错**，所以 `apply_group()` 每次先把三个旋钮**全部删掉**
再设自己那一个：只设自己那个的话，上一组留下的变量还在，量出来的是两个开关
叠加的结果——它不报错，只是让某一组的数字莫名其妙地好看或难看。有一条测试
专门钉这件事（跑 B 组时 C 组留下的 `S3_BEST_OF_N` 必须已经不在环境里）。

**预热一次再开始计时。** 第一次 consult 要把本体、证候表、检索索引这些惰性对象
建起来：沙盒实测第一组墙钟 **1.441 s**、后面几组 **0.05~0.09 s**——差的那 1.4 秒
全是初始化。不预热的话 A 组永远"最慢"，而那是排序造成的，不是这一组的性质。

## 二、三指标：沿用 R34 的定义，**分母各说各的**

1. **带本体出处的药味占比**（`herbs_grounded_ratio`）——分母是**这张方的药味数**；
2. **验证器一次过率**（`verifier_first_pass`）——第一轮就"无 veto、无 revise、
   且没有判不了的"；
3. **本体对语料的覆盖率**——分母是**医案语料里出现过的药名**，
   **语料侧、不随组变**，所以整份报告只报一次。

第三个当场就能跑（零 LLM）：按**种数** **0.3979**（230/578）、按**出现次数**
**0.7043**（3380/4799）。**两个都要报**：常用药覆盖得好、古籍写法的长尾覆盖差，
只报一个会各自误导一个方向。

### 这一节真正的设计是三条"没有数时怎么办"

**① legacy 组的验证器那一格是「不适用」，不是 0。** 符号验证器挂在 structured
这一支上（`S3Structured` 才有 `ontology_refs`）。把不适用写成 0，B 组看起来就像
"一次都没过"——那是拿一个不存在的失败去抹黑对照组。

**② "跑了但没产出结论"要跟"不适用"分开说。** 同样是空格子，前者是这一组真的
失败了（最该被看见），后者是这条路本来就没有这一步。合成一句话，最该被看见的
那种就消失了。

**③ 假后端的内容指标一律不出数。** `--backend fake` 的产出是固定假文本，
它的"带本体出处占比"只反映假数据长什么样。报告因此带一个
`content_metrics_valid` 标记，假后端下为 False，Markdown 里印 ⏳ 而不是数字。
能读的只有管道本身与调用数——而那也确实值得在沙盒里跑：R33 的教训就是
"演示配置从来没被跑过"。

## 三、外部基准：**没实测过的格式，只能做成可探测的**

`eval/sdt/` 那一套敢写"格式已实测验证"，是因为当时真把 TCMEval 拉下来跑了一遍。
这一轮做不到同一件事——写这套适配的沙盒**连不上数据源**（huggingface 403、
GitHub 按仓库授权）。两种应对里选了后一种：

- ✗ 按记忆写死字段名，报告里写"已接入"；
- ✓ 把字段映射写成**一张看得见的表**（`FIELD_CANDIDATES`），另配一个 `--probe`
  子命令，上机第一步先看真实数据长什么样。

探针报三类"多半映射错了"的形状，每一类各说各的话（合成一句"数据有问题"没法
照着修）：一条参考方都没读到 / 参考方超过 60 味 / 有记录没有参考方。
**跳过 `--probe` 的代价不是报错，是一份"所有人都得 0 分"的漂亮报告**——
SDT 那边踩过同一个形状（JSON 里的答案字段是空的，照着 Train 的字段名写代码
会得到一份全空的金标准而且不报错）。

打分三条口径：归一走 `core.herbs.normalize_herb`（**不另写一套字面比较**，
这个项目在同一堵墙上撞过三次）；macro 和 micro 都报、报告里写清用哪个；
**空方按"没作答"记，不按 0 分记**——把它们当 0 分混进均值，等于把"系统拒绝
作答"和"系统答错了"算成同一件事。

分数本身带着 `"scorer": "eval.mtcmb.score"` 走，**标明它不是官方分**。
MTCMB 若附官方打分脚本，以它为准。

## 四、跟开源中医模型（BianCang / ShizhenGPT）比：先把"能不能比"写死

**三条前提同时成立才能并排放进一张表**，缺一条就不该：

1. **同一个 split**（同样那批记录、同样的条数）；
2. **同一个打分脚本**（官方那份，或者两边都用 `eval.mtcmb.score`）；
3. **同样的作答条件**——尤其是安全否决：我们这侧会拒答一部分记录，对方不会。
   不标出来的话，我们的分会因为"拒答按没作答记"而偏高、或因为"拒答按 0 分记"
   而偏低，取决于谁在算。

正确的比法是**把它们当后端起起来**（`LLM_MODE=local_inproc`）跑同一份
`eval.mtcmb.run --solver baseline`；照抄论文里的分放进我们的表是第二种不可比。
这跟 R5 给蒸馏模型定的护栏是同一件事：**并列报、不覆盖、标清条件**。

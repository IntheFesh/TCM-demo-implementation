# R40 · 后端与推理链性能工程

一句话：**这一轮最重要的产出不是某个优化，是发现"验证器慢 2.4 秒"这个结论
本身是量具的 bug。**修掉量具之后，验证器是 0.4 ms，而真正大的两个数在别处：
一次响应体 2.85 MB（98.9% 是参考医案），以及 structured 提示词把变化段排在
了 1.25 MB 稳定段的前面、让前缀缓存在最大的那一块上命中率为 0。

所有数字都在本沙盒、`--backend fake` 下测得。**fake 后端把模型调用换成本地
函数**，所以量到的是"除模型之外这套东西能扛多少"，不是真实 LLM 下的延迟。
两种口径在本报告里从不并进一张表。

## 2. 量具自己的两个 bug（**这一节是本轮最重要的发现**）

### 2.1 「验证器 2429 ms」是假的

第一版 profile 报 `verify` = **2429 ms**，据此本轮的 KPI 是"验证器 ≤ 200 ms"。
那个数整个是错的，两个原因叠在一起：

1. **插桩包错了地方。** `core/formula_verifier.py` 顶上写的是
   `from core.ontology import Ontology, get_ontology`——函数对象在 import 时就
   绑进了它的命名空间。只给 `core.ontology.get_ontology` 包一层，验证器里那次
   调用**走不到包装**，于是 2.4 秒的本体层首次加载（1232 味 / 235 首）被记进了
   它的调用者 `verify`。
   这跟 R40 早先为 `verify_formula` 写的那条注释是**同一个坑的第二次**：
   「包在被用的地方，不是被定义的地方」。
2. **`TestClient` 不进上下文管理器时 lifespan 不跑。** 预热挂在 lifespan 上，
   所以那一版量的是"没有预热的第一次请求"——而那个状态在真实部署里不存在。

修掉之后：`verify` = **0.4 ms**（冷）/ **0.1 ms**（稳态）。

**一条只会绿的判据等于没有判据**：`tests/test_profiling.py` 现在有 20 条，
`tests/test_verifier_speed.py` 有一条 `herbs_batch` 只被调一次的计数断言，
就是为了让这类"看起来正常的错"红出来。

### 2.2 FastAPI 0.141 的快路径绕开了 `JSONResponse.render`

`serialize` 一段起初恒为空。原因不是插桩没生效，是 FastAPI 0.141 起有一条
快路径：`response_class` 是默认占位且存在 `response_field` 时，
`serialize_response(dump_json=True)` 直接产 bytes 再包一个裸 `Response`，
**`JSONResponse.render` 一次都不调**。真正的序列化点是
`fastapi.routing.serialize_response`，而它是 `async def`——
用同步 wrapper 包协程函数只会量到"创建协程对象"那几微秒。
所以 `ASYNC_TARGETS` 是一张单独的表。

## 3. 并行度审计表（每个串行点四问）

四问：① 这一段在等什么？② 它跟前后有真依赖吗？③ 并行之后结果会不会变？
④ 实测省了多少（收益为负就写负）？

| 串行点 | ① 在等什么 | ② 真依赖 | ③ 结果会变吗 | ④ 实测 | 处置 |
|---|---|---|---|---|---|
| 启动：本体层 → 检索器 | 本体层纯 CPU（jsonl 解析）；检索器等磁盘/网络（加载编码模型） | **无**（读不同文件） | 不会 | 串行 7602 ms → 并行 7760 ms，**−2.1%**（本沙盒模型下不动，那一步整个是"重试到 403"，没有可重叠的等待） | **已并行**，默认开，`WARMUP_PARALLEL=0` 关；负收益如实记 |
| 启动阶段 vs 开始监听 | ASGI startup 走不完 uvicorn 不处理请求 | 无（预热不是服务可用的前置条件） | 不会 | 开始监听从"最多等 120 s"变成 **< 1 s**（import 331–345 ms + lifespan≈0） | **已改**：先监听，`/health` 503 + 进度 |
| hybrid 三路检索（dense/bm25/graph） | dense 是 numpy 矩阵乘（**放开 GIL**）；bm25 纯 Python；graph 集合运算 | 无（各自从同一份 idxs 独立打分） | **会**——RRF 对输入顺序敏感，按完成顺序收就变了 | 本沙盒默认走 full_context，这条路没跑到；判据已钉（`tests/test_parallel.py` 三条） | **已并行**，键序固定 |
| 知识块：规律段 / 方剂段 / 药材段 | 都是本体内存查表 | 药材段**要用规律段的输出**——所以并行度是 2，不是 3 | 不会 | 0.2 ms → 0.6 ms，**+0.4 ms（+137%）**：两路都是亚毫秒级，线程创建的代价盖过收益。本沙盒的规律表近乎空（R35 的名医规律要真实医案）；规律段成为主项时才回正 | **已并行**，`PARALLEL_OFF=1` 可现场关；**负收益如实记** |
| `consult_many`（批量评测主干） | 每条主诉十几次 LLM 调用、几十秒到几分钟，**绝大部分在等 socket** | 无（条与条之间独立） | 不会（结果按下标对齐，`failures` 按 index 排序） | 默认并发 4（`CONSULT_MANY_WORKERS`）。不设"能开多少开多少"：上游限流、本地 vLLM 显存是硬上限 | **已并行** |
| 验证器七条规则 | 纯 CPU（查表 + 字符串比较） | 有（规则之间无依赖，但都要本体） | 不会 | 见 §4.2 | 规则本身不并行（亚毫秒，并行是纯亏），改成**批量查表** |
| 审计落盘 | flock + 追加写磁盘 | **有**：医生拿到 200 就意味着这张方进了审计链 | 不会 | 0.3 ms | **刻意保留同步**，见 §5 |
| SSE 事件队列 | 消费端（HTTP 生成器）的速度 | 有 | 会（丢掉 `need_input` = 追问永远等不到回答） | — | 两类事件两种策略，见 §4.4 |

## 4. 逐项优化（改前 → 改后，全部实测）

### 4.1 响应体裁剪：2,848,127 → 83,729 字节（**−97.1%**）

`full_context` 模式下 `refs` 是**整个语料**：

```
  results[0].refs   1,252,722 字节 / 1060 条   ← 响应体的 98.9%
  results[0].s3_structured   1,288
  results[0].s3                877
  graph                      1,186
```

1060 条参考医案没有任何界面能有意义地展示，而前端要在主线程上
`JSON.parse` 这 2.8 MB。

改法（`api/main.py` 的 `_cap_refs`，裁在**序列化边界**而不是链里——链内部
还要用全集算幻觉检查）：

- 下发上限 `REFS_IN_RESPONSE`（默认 20，环境变量可调）
- **被 `cited_case_ids` 引用的一条都不丢**，并排在最前（可追溯是这个项目的卖点）
- 其余按相似度补满
- 三个对照数一起下发：`refs_total` / `refs_sent` / `refs_cited` / `refs_truncated`
  ——项目铁律「任何数字都必须带对照」；只给 `refs` 不给 `refs_total`，
  前端会把"下发的条数"当成"检索到的条数"，那是个假数
- 前端那行小字改成「引自 20 条医案（本次检索到 1060 条，按相似度下发前 20 条；
  被结论引用的一条不漏）」

连带：`serialize` 4.3 ms → **0.6 ms（−86.9%）**。

### 4.2 验证器批量查表（7N → 1）

七条规则各自逐味 `ont.herb()`，而 `herb()` 每次都要跑一遍 `normalize_herb`
（去炮制前缀、去剂量、查别名）。12 味的方 = 7×12 = 84 次归一 + 84 次查表，
其中 72 次是重复劳动。

改法：`Ontology.herbs_batch(names)` 一次解析完，`BatchedOntology` 包一层
**委托**给七条规则共用（不改规则签名——那是医院增补规则时要照着写的公开契约）。

| | 一张 12 味的方，跑七条规则 |
|---|---:|
| 改前（逐条查） | 0.157 ms |
| 改后（批量） | **0.137 ms（−12.6%）** |
| 批量表命中 / 未命中 | 36 / **0** |

**绝对值很小，如实写小。** 它仍然做，因为 7N 次重复归一是白做的功，而且
本体层将来换成远程服务时（一次查表变成一次 RPC）这个倍数才是关键。

R40 的验收项「验证器耗时 ≤ 200 ms」：实测 **0.137 ms**，预算已写进测试
（`tests/test_verifier_speed.py::test_a_twelve_herb_formula_verifies_well_under_the_budget`）。

### 4.3 前缀缓存：稳定段 / 变化段拆分（**本轮第二个大发现**）

`prompts/v1/s3_structured.yaml` 里，每次问诊都变的两行
（`$elements_summary`、`$symptoms`）排在 **93%** 处，而全项目最大的一块稳定
内容 `$refs`（full_context 下 1060 条 / 1.25 MB）排在 **94%**——
**在变化段之后**。

前缀缓存按公共前缀命中。变化段一出现，它后面的内容就都掉出公共前缀，
于是那 1.25 MB 医案文本**每次问诊都要重新处理一遍**，缓存在最大的那一块上
命中率为 0。

R21 的 `core/context_prefix.assemble()` 已经为 legacy 那条路做对过这件事
（实测前缀缓存命中率 0.989），R33 新建 structured 模板时没有把那个次序带过来
——**同一个教训没有传到新入口**。

改后的位置（占模板长度的百分比）：

| 占位符 | 改前 | 改后 |
|---|---:|---:|
| `$physicians`（稳定） | 1% | 1% |
| `$physician_ids`（稳定） | 32% | 32% |
| `$refs`（稳定，最大一块） | 94% | **93%** |
| `$elements_summary`（变化） | 93% | **99%** |
| `$symptoms`（变化） | 93% | **100%** |

判据：`tests/test_prefix_cache_order.py` 14 条，包括
「任何一个稳定段都排在任何一个变化段之前」的 3×2 参数化组合、
「变化段之后不再有内容」、以及**两条路径（legacy assemble / structured 模板）
必须给出同一个答案**。理由写在 YAML 的 `notes` 而不是 `system`——
那段话是给改文件的人看的，送给模型只是白花 input token。

**这一项省的 token 数在本沙盒量不到**（fake 后端不记 token、也没有前缀缓存）。
省下来的量级可以直接算：full_context 下 `$refs` 是 1.25 MB 文本 ≈ 60 万 token
级，改前它每次都是 cache miss。真实数要在有真实后端的机器上按
`manifest` 的 `cached_tokens` 读——**没验过不等于通过**，这一项标⏳。

### 4.4 SSE 背压

改前 `events_q = queue.Queue()`——**无上限**。客户端读得慢或者卡住时，后台
线程照样按 token 频率往里塞 `s3_delta`（一次 S3 是千条量级），队列只涨不降，
而这中间没有任何一处会报错。几十条慢连接就能把进程的内存吃掉。

改后两类事件两种策略，**不能合并成一种**：

| 事件类 | 队列满时 | 为什么 |
|---|---|---|
| `s3_delta`（`SSE_DROPPABLE_EVENTS`） | **丢 + 计数** | 它们是"同一段文字的逐步生成"，终值由 `s3_done` / `done` 兜底；为它们阻塞后台线程等于让一条慢连接把整次问诊拖慢 |
| 其余（阶段完成、`need_input`、`done`、`error`） | **阻塞等**，超时（`SSE_PUT_TIMEOUT_SECONDS`=30s）后按"客户端不读了"收尾 | 丢任何一条都会让前端缺一段状态；`need_input` 丢了 = 追问永远等不到回答 |

丢了必须说出来：`deltas_dropped` 事件（单独一个事件，不塞进 `done` 的载荷
——`done` 的形状跟 `/api/consult` 的响应体是同一份契约），前端显示
「网络较慢，已跳过 N 条逐字增量（最终结果不受影响）」。

`SSE_QUEUE_MAXSIZE` 默认 2000：一次问诊的增量事件实测在千条量级，2000 给了
一倍余量，每条事件几十到几百字节 ≈ 几百 KB/流。
`finish()` 也加了超时——满队列上无限阻塞会让后台线程永远不退出。

### 4.5 启动：先监听，再预热

改前：lifespan 起预热线程然后**在 startup 阶段等它**，最多 120 s。ASGI 的
startup 没走完 uvicorn 不会开始处理请求——那段时间**端口开着、连接建得上、
一个请求都不答**，编排器的探针连得上却等不到响应，会把一个正常的进程判死。

改后：

- startup 立刻 yield → **开始监听 < 1 s**（import 331–345 ms + lifespan ≈ 0）
- 两项预热并行跑在后台
- `/health` 是**就绪**探针：没就绪回 **503 + 进度**，响应体照样完整
  （编排器看状态码，前端读响应体拿身份色）
- `/health/live` 是**存活**探针：永远 200。两个探针问的不是同一个问题，
  合成一个的代价是编排器分不清"还在热"和"已经死"
- `ready` 有三态：没人启动过预热（→ 200，惰性加载照常工作）/ 正在预热（→ 503）/
  跑完了（→ 200）。`started` 字段把前两种 `ready=true` 的来路分开
- 前端多一条中性色横幅「正在加载知识库（1/2）：检索器…」，轮询到就绪；
  轮询有上限（180 次），到顶就如实说"预热超过 N 秒还没完成"，不让一个转圈的
  横幅永远挂着

**启动预算**（R40 验收项：冷 ≤60 s / 热 ≤20 s）：

| | 本沙盒实测 | 预算 |
|---|---:|---|
| 开始监听 | **< 1 s** | — |
| 冷启动到 `/health` 回 200 | **8.97 / 9.15 / 9.53 s**（三次，中位数 **9.15 s**） | ≤60 s ✅ |
| 热启动（进程内第二次问诊起） | 逐段合计 **36.2 ms**（去掉 import） | ≤20 s ✅ |

### 4.6 投机执行 `verify_incremental`

只需要药名（+剂量）就能判的两条规则（`incompatible_pair`、`dose_exceeds`）
在 S3 还在流式输出、药名刚出来时就先跑一遍。

**这一项省的不是吞吐，是"知道得早"**：这两条是 veto 级——命中这张方根本不会
下发。等整段 S3 输出完（真实后端上几十秒到几分钟）再告诉医生"这张方作废了"，
那几十秒是白等的。

| | 4000 字的 S3 输出，每 40 字一帧 |
|---|---:|
| 投机关 | 0.051 ms |
| 投机开（10 次扫描） | **1.064 ms** |

**代价 1.01 ms 的 CPU，换最多几分钟的白等。** 扫描有三道保险：
只扫 `"herb_items"` 之后那一段（方名也叫 `name`）、每 400 字才扫一次
（正则扫的是累积全文，每帧扫是 O(n²)）、同一条 veto 只报一次。
提示的措辞写明「初步提示：基于尚未输出完的药味清单，最终以完整符号验证为准」
——半截输出上的结论可能作废，说成定论就是在临床界面上撒谎。

**结果不复用进最终验证**：`verify_formula` 照样把七条全跑一遍。
投机执行的定义就是"结果可能作废"。

### 4.7 revise 非思考（R34 已做，本轮核实并加判据）

重开那一步 `thinking="disabled"`：证型、治法、五步链都已经定了，要改的是
"把这味药换成归肝经的"这种照着反例改的局部修补。开思考在这一步是纯浪费
（单次 S3 开思考实测 260–479 s），而且反而更容易把已经对的部分想坏。
本轮核实代码仍是 `thinking="disabled", reasoning_effort=None`，未改。

### 4.8 连接复用（既有，本轮核实）

`OpenAICompatBackend.client` 是惰性构造 + 实例级缓存，而后端本身是进程单例
（`_llm_singleton`），所以 OpenAI SDK 底下的 httpx 连接池跨调用复用。
墙钟超时后 `abort_in_flight()` 丢掉客户端并回收连接池——卡住的那次读会随之
出错死掉，重试不会排在同一个坏连接后面。**未改，核实为已具备。**

### 4.9 重试退避（既有，本轮核实）

`generate()` 的重试循环走 `_backoff_seconds(attempt)`，SDK 自己的 `max_retries=0`
（否则 SDK 的静默重试不计入 `llm_calls`，"重试只在基类实现一份"这句话就不成立）。
**未改，核实为已具备。**

### 4.10 `consult_many` 并发

串行 → 默认并发 4（`CONSULT_MANY_WORKERS`）。**ContextVar 必须自己带过去**：
`ThreadPoolExecutor` 不复制上下文，而 `use_llm(backend)`（这次用哪个后端、
BYOK 的 key）和 `new_retry_stats()` 都挂在 ContextVar 上——不带的话工作线程
拿到的是默认后端，**不报错**，只是结果来自另一个模型。
`core/parallel.py` 里每个任务各 `copy_context()` 一份（同一个 Context
不能被两个线程同时进入）。

真实收益要在有真实后端的机器上量（每条主诉的墙钟几十秒到几分钟，
并发 4 理论上接近 4×）。本沙盒 fake 后端下一条主诉 36 ms，量不出有意义的
倍数——**标⏳，不编一个数**。

### 4.11 输出 token 削减

本轮核实到的实际情况：

- `S3_BEST_OF_N` 默认 **1**，所以输出 token 没有被 N 倍放大（N>1 是对照实验
  用的旋钮，R44 会在产品路径上禁用它）
- `revise` 一步已经关思考（§4.7），思考 token = 0
- 流式两路累积（content / reasoning）分开计数，`chars_content` /
  `chars_reasoning` 进 manifest，**输出规模可核**

没有找到"不牺牲输出质量就能砍掉"的输出 token：S3 的 `reasoning` 与
`reasoning_plain` 看起来重复，但后者是给患者/学生角色看的白话版，砍掉是
**产品降级**，不是优化。**这一项如实记为"已核实无可砍项"**，而不是编一个
削减比例。真正的大头在 **input** token，处置见 §4.3。

## 5. 刻意不做的一项：审计异步化

`append_audit()` 一次 **0.3 ms**（读尾行取 prev_hash + flock + 追加写）。
异步化能省的就是这 0.3 ms。

而处方导出那个端点**必须同步**：医生点了"导出"拿到 200，意味着这张方已经进了
审计链。改成异步的话，进程在那 0.3 ms 内被 kill（重启、OOM、滚动更新）就会
出现"药房拿到了方、审计链里没有这条记录"——三甲的审计要求下这是个合规缺陷，
换来的是 0.3 ms。

**不为性能牺牲正确性**：这一项的正确做法是量出来、指出代价不对等、把同步
保留，而不是把它异步掉再在报告里写"已优化"。

机制仍然建好了（`append_audit_async` / `flush_audit`，单线程池——哈希链要求
"读尾行、算 hash、追加写"整段串行，两个写线程会让链分叉），因为 R45 要把
哈希链扩展到**完整推理轨迹**：那条路上的记录不是发给药房的凭据，而且在问诊的
关键路径上。语义边界与判据先立清楚。

## 6. 压测（`scripts/loadtest.py`）

```bash
python -m scripts.loadtest --backend fake --sweep 1,2,4,8,16 --expect-503
```

| 并发 | 请求数 | p50 ms | p95 ms | p99 ms | 吞吐 req/s | 闸门 503 | 503 缺 Retry-After | RSS MB |
|---:|---:|---:|---:|---:|---:|---:|---:|---|
| 1 | 3 | 130.8 | 350.7 | 350.7 | 4.94 | 0 | 0 | 150 → 180 |
| 2 | 6 | 176.2 | 556.9 | 556.9 | 6.70 | 0 | 0 | 180 → 595 |
| 4 | 12 | 422.8 | 477.3 | 483.8 | **9.03** | 0 | 0 | 595 → 647 |
| 8 | 24 | 643.0 | 922.3 | 1096.8 | 8.99 | 6 | 0 | 647 → 690 |
| 16 | 48 | 1508.3 | 2203.7 | 2309.6 | 5.31 | 25 | 0 | 690 → 786 |

读数三条：

1. **吞吐在并发 4 见顶（9.03 req/s），到 16 反而掉到 5.31。**
   `MAX_CONCURRENT_CONSULTS` 默认就是 **4**——这个值不是拍的，它正好在拐点上。
   超过它的请求回 503 + `Retry-After`，**不排队**：排队的请求照样占着连接和
   线程池的槽，客户端也不知道自己在等什么。
2. **503 全部带 `Retry-After`**（表中"缺 Retry-After"列全 0）。没有它客户端只能
   瞎重试，而瞎重试会把一次尖峰变成持续过载。`--expect-503` 反过来验闸门
   **真的会挡**——一条只会绿的断言等于没有断言。
3. **吞吐按成功请求算。** 把 503 算进吞吐会让"闸门把请求全挡掉"看起来像
   "吞吐很高"。

内存：压测客户端与服务端在同一进程（`live_server` 就在本进程），所以 RSS 是
两者之和；有意义的是**档之间的增量**。150 → 786 MB 里最大的一跳是并发 2 那一档
（180 → 595 MB），那是预热（本体层 1232 味 + 检索索引）在后台跑完。
并发 4 → 16 只涨了 139 MB，即**每条并发问诊的增量在 10 MB 量级**。
